## What is interesting

- `REQUEST_HEADERS` is a target, with `!REQUEST_HEADERS:Cookie` **excluding** one
  header from the collection — the same syntax used in tuning.
- The transformation pipeline decodes **six** encodings before matching. The
  regex itself is simple; the transformations make it hard to dodge.
- Several XSS rules fire on the same payload: the score (20) is far above the
  threshold, which is why raising the threshold to 10 does not let this through
  (see the [anomaly-scoring experiment](../anomaly-scoring-experiment.md)).

## One-variable experiments

| `<script>alert(1)</script>` | match | blocked | 20 |
| `&lt;script&gt;alert(1)&lt;/script&gt;` (HTML entities) | match — `t:htmlEntityDecode` | blocked | 25 |
| `<SCRIPT >x` (case, space) | match — `(?i)`, `[^>]*` | blocked | 15 |
| `<scr ipt>` | no match (941160 still matches) | blocked | 5 |
| `script tag` (plain words) | no match | allowed | 0 |

The entity-encoded version also matched 932235 (`;script` looks like a shell
command after `&lt;`), raising the score to 25.

## Possible false-positive causes

Users legitimately writing about HTML (e.g. "my kid typed `<script>` into the
search box" — tested while hunting for FP-001: blocked with score 15).

## Safest tuning point

Route + argument exclusion for fields that are meant to hold markup; otherwise
leave it. Output encoding in the application is the real fix for XSS.
