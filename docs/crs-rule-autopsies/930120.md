## What stood out to me

`@pm` and `@pmFromFile` match phrases. Fast, no regex, and the list sits in a `.data` file next to the rules. Change the list, change the rule.

`t:normalizePathWin` flips `\` to `/` and resolves `./` and `../` before matching. So Windows style paths hit the same list.

Some rules show up twice in one transaction (930100, 930110). A CRS rule can match the same variable more than once, through `multiMatch` or several targets.

The traversal (`../`) gets caught by 930100 and 930110. The **file name** gets caught by 930120. Two independent signals. They stack.

## What triggers false positives

Docs or support text that names system files. "My `/etc/hosts` is wrong."

## Where I'd tune it

An exclusion scoped to one documentation or support field. Nowhere else.
