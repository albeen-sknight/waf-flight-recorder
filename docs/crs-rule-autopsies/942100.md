## How it gets there

1. Phase 2. ModSecurity URL decodes every target value, strips NUL bytes, and hands it to libinjection.
2. libinjection tokenizes `' OR 1=1--` into the fingerprint `s&1c`. That's on its list of SQL injection fingerprints.
3. The action says `block`. CRS runs in anomaly scoring mode, so `block` means `pass` here. The rule adds 5 points and moves on.
4. Rule 949110 (`REQUEST-949-BLOCKING-EVALUATION.conf`) checks `TX:BLOCKING_INBOUND_ANOMALY_SCORE` (5) against my threshold (5). Denied.

## One variable at a time (same endpoint, only `q` changes)

| `q` | 942100 | Decision | Score |
| --- | --- | --- | --- |
| `' OR 1=1--` | match | blocked | 5 |
| `' OR 1=1` (no comment) | match | blocked | 5 |
| `1 OR 1=1` (no quote) | match | blocked | 5 |
| `apple' --` | match | blocked | 5 |
| `O'Reilly` | no match | allowed | 0 |
| `O'Reilly OR` | no match | allowed | 0 |

A lone quote isn't SQL injection to libinjection. A quote followed by an operator or a comment is. That's why a customer called O'Reilly can still log in.

## What triggers false positives

Free text that tokenizes like SQL. Technical comments, code snippets, product names with a quote followed by an operator (`5' -- great`).

## Where I'd tune it

A runtime exclusion that removes **one argument** (`ctl:ruleRemoveTargetById=942100;ARGS:<name>`) on **one route**. Never `SecRuleRemoveById 942100`. That kills the rule on the login form too, and CRS-SQLI-003 is the Juice Shop admin login bypass.

## Regression test

`CRS-SQLI-001` and `CRS-SQLI-003` stay blocked with 942100 in the match list. `NRM-007` (a normal login) stays allowed.
