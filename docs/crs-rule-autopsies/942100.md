# Autopsy — CRS 942100: SQL Injection Attack Detected via libinjection

| Field | Value |
| --- | --- |
| Rule ID | 942100 |
| File / line | `REQUEST-942-APPLICATION-ATTACK-SQLI.conf`, line 46 |
| Category | `attack-sqli`, paranoia level 1 |
| Phase | 2 (request body) — needs POST/JSON arguments, not only the query string |
| Targets | `REQUEST_COOKIES`, `REQUEST_COOKIES_NAMES`, `REQUEST_HEADERS:User-Agent`, `REQUEST_HEADERS:Referer`, `ARGS_NAMES`, `ARGS`, `XML:/*`, `XML://@*` |
| Transformations | `t:none,t:utf8toUnicode,t:urlDecodeUni,t:removeNulls` |
| Operator | `@detectSQLi` — libinjection, a SQL **tokenizer**, not a regular expression |
| Actions of note | `block`, `capture`, `multiMatch`, severity CRITICAL, `setvar:tx.inbound_anomaly_score_pl1=+%{tx.critical_anomaly_score}`, `setvar:tx.sql_injection_score=+…` |
| Triggering request | CRS-SQLI-001 `GET /rest/products/search?q=' OR 1=1--` (sample: [`phase1-crs-sqli-blocked.json`](../../evidence/sanitized-samples/phase1-crs-sqli-blocked.json)) |
| Matched variable | `ARGS:q` |
| Matched data | libinjection fingerprint `s&1c` (string, logical operator, number, comment) |
| Score contribution | +5 (CRITICAL) |
| Final decision | Blocked by **949110** in phase 2, total score 5 = threshold 5 |

## How it reaches the decision

1. Phase 2: ModSecurity hands every value of the targets to libinjection after URL-decoding and removing NUL bytes.
2. libinjection tokenizes `' OR 1=1--` and produces the fingerprint `s&1c`, which is in its list of SQLi fingerprints.
3. The rule's action is `block`; CRS runs in anomaly-scoring mode, so `block` = SecDefaultAction = `pass`. The rule only adds 5 points.
4. Rule 949110 (`REQUEST-949-BLOCKING-EVALUATION.conf`) compares `TX:BLOCKING_INBOUND_ANOMALY_SCORE` (5) with the threshold (5) and denies.

## One-variable experiments (same endpoint, only `q` changes)

| `q` | 942100 | Decision | Score |
| --- | --- | --- | --- |
| `' OR 1=1--` | match | blocked | 5 |
| `' OR 1=1` (no comment) | match | blocked | 5 |
| `1 OR 1=1` (no quote) | match | blocked | 5 |
| `apple' --` | match | blocked | 5 |
| `O'Reilly` | no match | allowed | 0 |
| `O'Reilly OR` | no match | allowed | 0 |

A quote alone is not SQL injection to libinjection; a quote followed by an
operator/comment structure is. That is why a customer named O'Reilly can log in.

## Possible false-positive causes

Free text that tokenizes like SQL: technical comments, code snippets, product
names with quotes followed by operators (`5' -- great`).

## Safest tuning point

A runtime exclusion removing **one argument** (`ctl:ruleRemoveTargetById=942100;ARGS:<name>`)
on **one route** — never `SecRuleRemoveById 942100`, which would also disable
the rule for the login form (CRS-SQLI-003, the Juice Shop admin-login bypass).

## Regression test

`CRS-SQLI-001` and `CRS-SQLI-003` must stay blocked with rule 942100 in the
match list; `NRM-007` (normal login) must stay allowed.
