# FP-002: Juice Shop's own PUT/DELETE requests, blocked by CRS 911100

| | |
| --- | --- |
| Status | Fixed (configuration), regression-tested |
| Rule | CRS 911100, Method is not allowed by policy, CRITICAL |
| Fix | `tx.allowed_methods` (rule 900200) in `modsecurity/crs-setup.conf` |
| Scenarios | NRM-003 (PUT), NRM-004 (DELETE), MTH-001/002 (WebDAV still refused) |

## Before

With the CRS defaults (`tx.allowed_methods=GET HEAD POST OPTIONS`):

```
PUT    /api/BasketItems/1  {"quantity": 2}   BLOCKED 403  911100 + 949110  score 5
DELETE /api/BasketItems/1                    BLOCKED 403  911100 + 949110  score 5
```

Samples: [`fp002-before-put-blocked-911100.json`](../../evidence/sanitized-samples/fp002-before-put-blocked-911100.json), [`fp002-before-delete-blocked-911100.json`](../../evidence/sanitized-samples/fp002-before-delete-blocked-911100.json).

Changing how many juices are in your basket. Removing one. Core shop stuff, and both dead.

## Why this isn't an exclusion

911100 did exactly what it was told. The config just didn't describe this app. CRS exposes the method list as a setting, so the fix is the setting:

```apache
setvar:'tx.allowed_methods=GET HEAD POST OPTIONS PUT PATCH DELETE'
```

## After

`PUT /api/BasketItems/1` gets through, nothing matches ([`fp002-after-put-allowed.json`](../../evidence/sanitized-samples/fp002-after-put-allowed.json)).

## The trade-off, and what claws it back

PUT, PATCH and DELETE now pass on every route. Two of my rules narrow that back down:

- **100010** refuses WebDAV methods (PROPFIND, MKCOL, …) with a 405.
- **100060** refuses `DELETE /api/Feedbacks/*` specifically. That's a Juice Shop challenge.

## A note on `@within`

911100 uses `!@within %{tx.allowed_methods}`. Substring test. With PATCH on the list, a method called `PAT` sails through too. That's exactly why my rule 100010 uses an anchored `@rx` instead (see `custom-rules/110-method-policy.conf`).
